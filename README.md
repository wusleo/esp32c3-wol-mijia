# ESP32-C3 远程唤醒器 · 米家/小爱 + 电池供电

一块十几块钱的 ESP32-C3 SuperMini，接在台式机旁边的 USB 口上，就能让**小爱同学开口把电脑叫起来**——而且整机可以只靠一节 18650 供电，跑上几个月。

做完之后你会得到：

- 对小爱说「打开电脑」，台式机从**完全关机**状态启动
- 米家 App 里手动点按，效果一样
- 平时处于 light sleep，平均电流亚毫安级，一节 18650 撑几个月
- WiFi 掉线自己重连，MQTT 断了自动恢复，装进机箱就不用管
- 想改固件时发一条 MQTT 指令让串口复活，不用拆机箱、不用按任何键

板子一旦塞进机箱就摸不到了，所以「省电」和「可维护」这两个互相矛盾的目标必须同时成立——本项目大部分设计取舍都来自这里，细节见[踩坑记录](#9-踩坑记录)。

## 1. 实现的功能

| 功能        | 说明                                           |
| --------- | -------------------------------------------- |
| 远程开机      | 巴法云 MQTT 下发 `on`，ESP32 发送 WOL 魔术包            |
| 小爱同学语音控制  | 巴法云同步到米家后，对小爱说「打开电脑」                         |
| 手机 App 控制 | 米家 App 内手动点按；建议建成「手动控制」按钮，一键触发（见 [6.3](#63-第三步米家里建一个手动控制一键按钮)） |
| 超低功耗      | light sleep + WiFi modem sleep，一节 18650 数月待机 |
| 断线自愈      | WiFi 掉线后重新扫描选最强 AP 重连，MQTT 自动重连              |
| 远程调试窗口    | MQTT 下发 `debug` 让芯片保持清醒 10 分钟，串口恢复，可直接烧录     |
| 按键旁路      | 按住 BOOT 上电则不进入睡眠，方便本地调试                      |
| 网页配网      | 烧完直接上电，手机连 `WOL-Setup-XXXX` 热点，网页里填 WiFi / 巴法云 / MAC，保存即生效 |

> **以上功能均已在新板真机全流程跑通**：手机连 `WOL-Setup-E4F5` → 网页填配置 → 保存重启 → 连 WiFi → 连巴法云 → 米家点按 → 处于 light sleep 的板子收到 MQTT 指令并发出魔术包 → 台式机从**完全关机**状态启动成功。
>
> 网页配网这条链路（SoftAP → HTTP 页面 → DNS 劫持 → 写 NVS → 重启连网）是实测过的，不是纸面功能。
>
> **关机不支持。** WOL 只能「叫醒」，不能「关机」。想要远程关机，请在目标机上跑一个接收端脚本，或用支持网络唤醒/关机的中控方案。

## 2. 为什么不直接用 Arduino 方案

社区里流传的 WOL 固件大多是 Arduino 写的，代码简单，但**省电这条路是死的**。

原因在 Arduino-ESP32 的预编译二进制库：`sdkconfig` 里 `CONFIG_PM_ENABLE` 没有打开。这意味着：

```c
esp_pm_configure(&cfg);   // 永远返回 ESP_ERR_NOT_SUPPORTED
```

电源管理框架整个不参与编译，light sleep 根本无从谈起。你能用的只有 `WiFi.setSleep(true)`（modem sleep），实测电流停在 **11mA** 左右——一节 2000mAh 的 18650 大约撑 7 天。

换成 ESP-IDF 自己编译后：

```
I (6403) pm: Frequency switching config: CPU_MAX: 160, APB_MAX: 80, APB_MIN: 40, Light sleep: ENABLED
I (6403) LS: [OK] esp_pm_configure = ESP_OK, light sleep enabled
```

电流可以压到亚毫安。这是本项目必须放弃 Arduino 的唯一原因。

**采购要点**

- **认准 TO-92**。同型号的 SOT-23 / SOT-89 是贴片，必须焊，而且比 TO-92 难焊得多。

- **别买 AMS1117-3.3**。静态电流 5mA，是 HT7333 的上千倍，电池方案里等于自杀。
- 电容耐压选 10V 以上，100µF 电解**有极性**，外壳印白边那侧是负极。

### 为什么是 LDO，不是升压模块

这是电池方案里最容易选错的一环。很多教程（包括我最初看的那份）都用 MT3608 把 3.7V 升到 5V 再喂给板子，**对于超低功耗场景这是个坑**：

| 方案 | 转换效率 | 模块自身静态电流 | 说明 |
|---|---|---|---|
| MT3608 升压到 5V，再走板载 LDO 降到 3.3V | 约 46%（0.7 × 0.66） | **1~2 mA** | 两级串联，且 MT3608 空载就吃 1~2mA，比整个系统还耗电 |
| LDO 直接 3.7V → 3.3V，绕过板载 LDO | 约 89% | 2.5 µA（HT7333） | 单级，损耗只有压差 |

目标负载只有 0.3mA 量级时，MT3608 那 1~2mA 的静态损耗**直接把续航砍掉一个数量级**。所以电池方案一律用低静态电流 LDO。

LDO 选型的唯一硬指标：**静态电流（Quiescent Current）必须是 µA 级**。

- ✅ **HT7333**（250mA / 静态 2.5µA typ、4µA max / 压差 120mV@30mA）—— 首选，有 TO-92 直插
- ✅ ME6211C33（500mA / 40µA）、MCP1700（250mA / 1.6µA）—— 备选，多为贴片封装
- ❌ **AMS1117（5mA 静态电流）—— 绝对不能用**，它自己就比整机耗电十几倍

C3 在 14dBm 发射时峰值电流约 240mA，所以 LDO 输出能力至少要 250mA——HT7333 正好卡在这个数上，配 100µF 输出电容扛瞬时峰值够用；想让余量更宽裕可以看 ME6211C33（500mA），代价是静态电流大 16 倍。

HT7333 压差小（30mA 时仅 120mV）意味着 18650 一路放到 **3.45V 左右**输出都还稳在 3.3V。再往下 LDO 开始掉压，但 C3 的工作下限是 3.0V，所以电池实际能榨到接近 3.1V，容量利用率相当高。

### 换 TPS63020 行不行

行得通，但有两个坑，**不建议用**。

先说它的好处：TPS63020 是 TI 的升降压芯片，输入 1.8–5.5V，输出可调，峰值效率 96%，电池掉到 3.3V 以下还能稳住 3.3V。成品模块已经带好电感电容，接线就能用，不需要焊——这一点确实比裸 LDO 省事。

**坑一：成品模块出厂默认静态电流 6mA**

模块商品页普遍这么标：

> Static power consumption: 6 mA (idle), 50 µA (power saving mode)
> Power Saving Mode (PS): ... The module is disabled by default.

默认 PS 引脚被拉在「禁用节能」，芯片跑强制 PWM。6mA × 24h = 144mAh/天，一节 2000mAh 的 18650 **撑不到两周**。

想降到 50µA，得把模块上的 SB1 焊桥断开、再给 PS 引脚加电平——**又回到焊接，而且比焊 LDO 更细**。

**坑二：负载太轻，效率优势用不上**

| | HT7333 LDO | TPS63020（启用节能后） |
|---|---|---|
| 静态电流 | **2.5 µA** | **50 µA** |
| 轻载表现 | 无开关损耗 | 0.5mA 以下效率掉到 70~85% |
| 外围元件 | 一颗电容 | 模块自带 |
| 成本 | ¥1~3（TO-92 直插） | ¥20~30 |

负载 0.5mA 时的实际电池电流：

- **LDO**：500 µA + 2.5 µA ≈ **503 µA**
- **TPS63020**：1.65 mW ÷ 85% + 50 µA ≈ **580 µA**

**结论**：如果是为了省掉焊接，选 **TO-92 直插的 HT7333** 就行——三根长脚插端子就行，比改 TPS63020 的焊桥简单得多，静态电流还低 16 倍。TPS63020 真正的价值是「电池要放到 2.8V」，本项目用不上。

### 接线

**方案 A：插电**

没有接线。充电头插板子的 USB-C 口就完事。

> 调试烧录时注意：线必须是**数据线**，只充电线会让电脑完全认不到板子，现象跟板子坏了几乎一样。

**方案 B：电池**

先看最省事的接法。

#### 极简接法：4 根线，不接电容

```
电池盒 +     ──────────► HT7333 VIN
电池盒 −     ──┬───────► HT7333 GND
               └───────► ESP32-C3 GND
HT7333 VOUT  ──────────► ESP32-C3 3V3
```

1. HT7333 三根脚分别插进三个端子孔（一根脚一个孔）
2. 电池盒的 `+` 线接「VIN」端子
3. 电池盒的 `−` 线接「GND」端子；从同一个端子再引一根线到板子的 `GND`
4. 从「VOUT」端子引一根线到板子的 `3V3`
5. 上电池，量板子 `3V3` 对 `GND`，**3.2~3.4V 就成功了**

##### 不用学认引脚：多买两颗

HT7333 的 TO-92 有两种引脚排列，买到哪种看厂家批次：

| 排列 | 正面（印字朝自己、引脚朝下）从左到右 |
| --------- | --------------------------- |
| TO-92-A   | **GND** · **VIN** · **VOUT** |
| TO-92-B   | **VIN** · **GND** · **VOUT** |

不必研究手里是哪一种，**直接按 TO-92-A 接上、量输出**：

| 量到的电压 | 说明 | 处理 |
| ---------- | ----------- | ------------ |
| 3.2~3.4V | 接对了 | 收工 |
| ≈ 电池电压（4.2V） | VIN / VOUT 反了 | 断电，这两根对调 |
| 0V | 中间那根不是 GND | 换一颗，按 TO-92-B 接 |

HT7333 一块钱一颗，**买 3 颗备着**。烧掉一颗的成本，远低于研究万用表半小时。

##### 电容能不能省

能，先不接。理由：

- 18650 内阻只有 50~100mΩ，240mA 发射峰值在电池上只掉 15~25mV，LDO 输入基本不塌
- HT7333 输出能力 250mA，正好覆盖这个峰值
- SuperMini 板载 3V3 网络上本来就有 10µF + 100nF 陶瓷电容

**什么时候需要补**：电池老化内阻变大、端子虚接、线太长太细。症状是**随机重启、日志莫名从启动重新开始**。真遇到了，在 VOUT 与 GND 之间补一颗 100µF 电解即可，不用重新布线。

##### 想精确确认引脚：万用表二极管档

前面的「接错就换一颗」是图省事。如果手边有万用表、想一次接对，用二极管档测：

1. 黑笔固定在任意一根脚上，红笔依次点另外两根；
2. 两次都显示 0.5~0.8V 压降的那根脚，**就是 GND**（内部 ESD 二极管从 GND 指向各引脚）；
3. 剩下两根里分 VIN / VOUT：红笔点 A、黑笔点 B，若显示 0.5~0.9V 压降，则 **A 是 VOUT、B 是 VIN**（内部 PMOS 体二极管由 VOUT 指向 VIN）；
4. 反向再测一次应该没有读数，用来复核第 3 步。

##### 没有万用表：限流试接

电池正极串一颗 **100Ω 电阻**再接到 VIN，通电后量 VOUT 对 GND：

- 读到 **3.2~3.4V** → 接对了
- 读到接近 4.2V（等于输入）→ VIN/VOUT 反了，断电阻对调
- 读到 0V → GND 或 VIN 接错，立刻断开重来

100Ω 把电流限制在 40mA 以内，接错也不会烧，只是别一直通着。

#### 完整接法：把电容也并上（可选）

想一次到位、不赌运气，就加上电容，把下面两颗都并到输出端。

##### 带电容的接线

这是**全程不需要烙铁**的接法。充电时把 18650 取下来用外置充电器充。

```
 18650 电池盒 (+) ────────► VIN ┐
                                │
 18650 电池盒 (−) ──┬─────► GND ┤  HT7333
                    │           │  (TO-92)
                    │      VOUT └──────┬───────► ESP32-C3  3V3
                    │                  │
                    │                  ├───────► 100µF 电解 (+)
                    │                  └───────►  10µF 独石
                    │
                    ├──────────────────────────► 100µF 电解 (−)
                    ├──────────────────────────►  10µF 独石 (−)
                    └──────────────────────────► ESP32-C3  GND
```

按这个顺序接，接完先别上电池：

1. 把 HT7333 三根脚分别插进三个端子的孔里（每根脚各占一个端子位）；
2. 电池盒正极线接「VIN」端子，负极线接「GND」端子；
3. 从「GND」端子再引出一根线，接到 ESP32-C3 丝印标 `G` 或 `GND` 的脚；
4. 从「VOUT」端子引出一根线，接到 ESP32-C3 丝印标 `3V3` 的脚；
5. 两颗电容全部并在 **VOUT 与 GND 之间**（靠近板子一侧）：100µF 电解正极接 VOUT、白边一侧接 GND；10µF 独石不分极性，跨在 VOUT 与 GND 上即可；
6. 输入侧也可以再并一颗 10µF（手册建议 CIN=COUT=10µF），不加也能工作，加了更稳。

接完用万用表复核：**VOUT 对 GND 应为 3.2~3.4V，ESP32-C3 的 `3V3` 对 `GND` 应与之一致。** 确认无误再插电池。

> ⚠️ **电解电容有极性**，接反会鼓包甚至炸开。外壳印着一条白边的那侧是负极。
>
> ⚠️ 端子拧紧后再拉一下线，虚接会让板子在发射瞬间掉电重启，现象是「随机重启、日志无故从启动开始」。

#### 加 TP4056：机箱内充电（可选）

加了 TP4056 就可以不拆电池、直接插 USB 充电。**代价是它需要焊 4 根线**（模块上的 `B+` `B-` `OUT+` `OUT-` 是焊盘，不是端子），所以这一步不算免焊。

```
18650 电池盒 +  ──→ TP4056  B+
18650 电池盒 −  ──→ TP4056  B−
TP4056  OUT+  ──→ HT7333 的 VIN（后面同上面的带电容接法）
TP4056  OUT−  ──→ HT7333 的 GND
```

TP4056 的 Type-C 口接 5V 充电头即可。**注意：充电时不要同时插 ESP32-C3 的 USB 口**（原因见下面的铁律 1）。

> ### ⚠️ 接 3V3 引脚的两条铁律
>
> **1. 绝不能同时插 USB。**  
> 板载 LDO 的输出端和 USB 供电路径都挂在 3V3 网络上，两边同时供电会互相倒灌，
> 轻则重启，重则烧掉板载 LDO 或稳压芯片。
>
> **2. 接的是 `3V3` 脚，不是 `5V` 脚。**  
> 接到 5V 脚就会走进板载那颗 AMS1117（或同类），静态电流直接把省电努力清零。

### 备选方案：MT3608 升压到 5V

只有一种情况适合它：你不打算用电池长期供电，或者手上现有材料只有升压模块。
接线如下（依然要注意下面那条警告）：

```
18650 ──> TP4056(B+/B-) ──> MT3608(IN+/IN-) ──> ESP32-C3(5V/GND)
                                                        └── 100µF + 10µF 到 GND
```

> **MT3608 出厂默认输出可能是 12V 甚至更高。**  
> 先只接电池输入、不接 ESP32，用万用表量输出，**把电位器调到 5.0V**，再接线。  
> 直接接板子基本一上电就烧。

### 关于拆 LED

C3 SuperMini 板载一颗红色电源 LED，常亮约 1.5mA。这个数字看着小，但 light sleep 本身的平均电流只有 0.3~~0.6mA——\*\*这颗灯比芯片本身还耗电 2~~5 倍\*\*。

如果追求极限续航，把它旁边的限流电阻拆掉（或直接拆 LED）。不拆也能用，只是所有功耗优化在实测上都看不出差别。详见 [8.2 节](#82-板载-led-是隐藏的耗电大户)。

## 4. 软件环境与编译

### 环境

- **ESP-IDF v5.x**（本项目在 v5.5.6 上验证）
- 不需要 Arduino IDE，也不需要 PlatformIO

### 方式 A：命令行

进入工程目录：

```bash
idf.py set-target esp32c3
idf.py build
idf.py -p COMx flash monitor
```

**不需要先配置。** 配置可以烧完再填——首次上电会自动开一个配网热点（见下一节）。

> **Windows 提示**：如果编译卡在某个进度不动、CPU 占用为 0，多半是 `ccache` 包装层把 gcc 子进程挂起了。  
> 用 `idf.py --no-ccache build` 可以绕开。这个问题在国内几台机器上都复现过。

### 方式 B：VS Code 图形界面

装扩展 **ESP-IDF**（`espressif.esp-idf-extension`），用 VS Code 打开工程目录。

**v2.x 版本的配置键全变了**，旧教程里的 `idf.espIdfPath` / `idf.toolsPath` 已经不存在，别再照着填。仓库里带了一份模板，复制成实际配置：

```bash
cp .vscode/settings.json.example .vscode/settings.json
```

内容是这样（三处路径改成你自己的，`idf.port` 改成你的串口）：

```json
{
  "idf.customExtraVars": {
    "IDF_PATH": "D:\\Espressif\\frameworks\\esp-idf-v5.5.6",
    "IDF_TOOLS_PATH": "D:\\Espressif",
    "IDF_PYTHON_ENV_PATH": "D:\\Espressif\\python_env\\idf5.5_py3.11_env",
    "ESP_ROM_ELF_DIR": "D:\\Espressif\\tools\\esp-rom-elfs\\20260528",
    "IDF_CCACHE_ENABLE": "0"
  },
  "idf.extensionActivationMode": "always",
  "idf.flashType": "UART",
  "idf.port": "COM11",
  "idf.flashBaudRate": "460800",
  "idf.enableCCache": false
}
```

把三处路径改成你自己的安装位置（`ESP_ROM_ELF_DIR` 结尾那个日期目录名，以 `tools/esp-rom-elfs/` 下实际存在的为准），`idf.port` 改成你的串口。

**`IDF_PATH`、`IDF_TOOLS_PATH`、`IDF_PYTHON_ENV_PATH` 三个一个都不能少。**

扩展判断「有没有一套能用的 IDF」的逻辑是：前两个目录都存在 → 从第三个拼出 `Scripts\python.exe`。缺任何一个键，右下角就会冒出来：

- `No ESP-IDF Setups found`
- `The extension configuration is not valid`
- `cmake executable not found` / `esptool.py is missing or not accessible`

这几个报错看着像扩展装坏了，实际只是少了一行配置。改完 `Ctrl+Shift+P` → `Developer: Reload Window` 重载窗口即可。

**目标芯片不用手动设**：`sdkconfig.defaults` 里已经写死 `CONFIG_IDF_TARGET="esp32c3"`，干净 clone 下来（没有 `sdkconfig`、没有 `build/`）第一次编译就会自动用 esp32c3。

> **不要点 `ESP-IDF: Set Espressif Device Target`。** 一旦在那里选了 `esp32`，工程就变成 xtensa 目标，`sdkconfig` 和 `CMakeCache` 里的 target 都会被改写。这个状态很隐蔽：编译照样成功、bin 大小正常，只有烧录时才报 `This chip is ESP32-C3, not ESP32. Wrong --chip argument?`。
>
> 误点了就执行 `idf.py set-target esp32c3` 清掉 `build/` 重来（会丢失 `sdkconfig` 里手改的项）。

配好后底部状态栏会出现 `esp32c3` 和串口号，然后 `Ctrl+Shift+P` 执行：

| 做什么 | v2.x 命令（英文界面 / 中文界面） |
|---|---|
| 选串口 | `ESP-IDF: Select Port to Use (COM, tty, usbserial)` / `选择要使用的端口` |
| 编译 | `ESP-IDF: Build Your Project` / `构建项目` |
| 只编 app | `ESP-IDF: Build App Only` / `仅构建应用程序` |
| 烧录 | `ESP-IDF: Flash (UART) Your Project` / `通过 UART 接口烧录项目` |
| 看日志 | `ESP-IDF: Monitor Device` / `监视设备` |
| 查环境 | `ESP-IDF: Doctor Command` / `诊断命令` |

> **v2.x 的命令名和网上大多数教程都不一样**。旧教程写的 `Build your project` / `Flash your project` 在 v2.x 里已经不存在，搜索不到不是你的问题。找不到命令就直接搜 `ESP-IDF` 看完整列表。

> 第一次编译前右下角提示 `compile_commands.json is missing` 是正常的，编译一次就会生成，不用管。

## 5. 配置：配网页或 menuconfig

私人参数（WiFi、巴法云、目标 MAC）有两个来源，优先级 **NVS（配网页填的）> menuconfig**：

| 来源 | 怎么填 | 适合谁 |
|---|---|---|
| **配网页面** | 烧完直接上电，手机连热点进网页填 | 绝大多数人，不需要装编译环境 |
| `menuconfig` | 编译前填，固化进固件 | 想批量做几块、或不想留配置页 |

配网页保存过一次之后，menuconfig 里那几项就再也不起作用了。

定义在 `main/Kconfig.projbuild`，运行时由 `main/app_config.c` 合并成一份配置，其余模块只认这一份。

---

### 5.1 配网页（推荐）

不用改代码、不用碰 menuconfig，烧完第一次上电就能用手机配好。全程三分钟。

#### 第 1 步：确认设备进了配网模式

烧录完成后设备自动重启。如果 flash 里没有完整配置（全新板子，或刚擦过 NVS），它会自己开热点，串口打印：

```
W (1234) provisioning: ==============================================
W (1234) provisioning:  config incomplete -> provisioning mode
W (1234) provisioning:  hotspot : WOL-Setup-E4F5  (open, no password)
W (1234) provisioning:  open    : http://192.168.4.1
W (1234) provisioning: ==============================================
```

热点名的规则是 `WOL-Setup-` + 芯片 MAC 的后两字节。比如 MAC 是 `a0:b1:c2:d3:e4:f5`，热点就是 `WOL-Setup-E4F5`。

**怎么算成功**：手机 WiFi 列表里出现一个 `WOL-Setup-` 开头的开放热点。

#### 第 2 步：手机连上这个热点

- 没有密码，直接连
- **连上后把移动数据关掉**。安卓和 iOS 都会因为「此网络无法上网」自动切回流量，那样就打不开配置页，白折腾一轮
- iOS 提示「无互联网连接」时选「仍要连接」

**怎么算成功**：WiFi 显示已连接（旁边带感叹号是正常的）。

#### 第 3 步：打开配置页

浏览器地址栏手动输入：

```
http://192.168.4.1
```

必须带 `http://`，别让浏览器自动跳 https。多数手机会自动弹出（captive portal），没弹就手输。

**怎么算成功**：看到标题「远程唤醒器 · 配网」，下面三张卡片。

#### 第 4 步：填 WiFi

| 字段 | 怎么填 | 注意 |
|---|---|---|
| WiFi 名称 | 点「扫描」从列表选，或手动输入 | **只支持 2.4G**。双频合一的路由器扫到 5G 会连不上 |
| WiFi 密码 | 如实填 | 开放网络留空 |

#### 第 5 步：填巴法云

先登录 `cloud.bemfa.com`，取两样东西。

**① UID** —— 个人中心里的 32 位十六进制串，形如 `0123456789abcdef0123456789abcdef`。它同时充当 MQTT 的用户名和密码。

**② 主题值** —— 设备云列表里，主题卡片上那行字母数字，形如 `aB3xY9kLm006`。

**这一步是整个配置里最容易错的地方**，我实际就栽在这：

```
主题值   aB3xY9kLm006     ← 填这个
昵称     客厅电脑          ← 别填这个
```

填成昵称，设备照样能连上巴法云（日志里 `bemfa: connected` 一切正常），但它订阅的是一个不存在的主题。结果就是：米家/小爱发的指令永远到不了设备，控制台一直显示「订阅者：离线」，看起来像设备坏了。

判断依据很简单：**主题值里不会出现中文**。配置页现在会在提交时检查，带中文直接拦下并弹窗提示。

#### 第 6 步：填电脑 MAC

必须是**有线网卡**的 MAC。

Windows 上开 PowerShell：

```powershell
ipconfig /all
```

找到「以太网适配器 以太网」那一段（**不是** WLAN），复制「物理地址」，形如 `AA-BB-CC-DD-EE-FF`。填的时候横线冒号都行：`AA:BB:CC:DD:EE:FF`。

填 WiFi 网卡的 MAC 没有意义——关机后无线网卡完全断电，收不到魔术包。

#### 第 7 步：保存

点「保存并重启」。之后依次是：写 NVS → 关热点 → 重启 → 连你的 WiFi → 连巴法云，大约 10~15 秒。

#### 第 8 步：验证

三个检查点，从设备侧往云端走：

**① 串口（最可靠）**

```
I (6280) wifi: got ip 192.168.1.43
I (6400) bemfa: connected, subscribe "aB3xY9kLm006"
I (6400) main: magic dest  : auto:9
I (6400) main: grace period 30000 ms ...
```

| 看到 | 说明 |
|---|---|
| `got ip 192.168.x.x` | WiFi 通了 |
| `bemfa: connected` | MQTT 通了 |
| `subscribe "xxx"` | **这里必须和你填的主题值完全一致** |
| `grace period 30000 ms` | 30 秒调试窗口，之后进 light sleep、串口静音 |

**② 巴法云控制台** —— 那个主题的「订阅者」从「离线」变成在线。

**③ 手机热点** —— `WOL-Setup-XXXX` 消失（热点已关闭）。

#### 第 9 步：发一条指令试试

在巴法云控制台点「在线调试」，或直接在米家里操作，发 `on`。

串口（还在 30 秒窗口内时）会打出：

```
I (16402) main: cmd "on"
I (16402) wol: broadcast address derived from netif: 192.168.1.255
I (16412) wol: magic packet sent to 192.168.1.255:9 for aa:bb:cc:dd:ee:ff
```

巴法云的调试面板会收到设备回的两条消息：`ack:6f6e`（`on` 的十六进制，用于确认平台到底发了什么）和 `wol:sent`。

电脑处于关机状态时，这条指令会让它开机。之后就再也不用碰板子了。

> 实现见 `main/provisioning.c`（热点 + HTTP + DNS 劫持）和 `main/index.html`（配置页）。
> 页面是编译时用 `EMBED_FILES` 嵌进固件的，改文案不用动 C 代码。

**想重新配网怎么办**

配网页只在配置不完整时出现。想改配置，把 NVS 清掉即可：

```bash
idf.py -p COMx erase-flash      # 连固件一起擦
idf.py -p COMx flash            # 重新烧，开机就是配网模式
```

> 只擦 NVS 不重烧也行：`esptool.py -p COMx erase_region 0x9000 0x6000`，
> 但分区偏移随分区表变化，`erase-flash` 更省事。
>
> **换 WiFi 密码不用再拆机**：从 v1.1.1 起，开机后连续 90 秒拿不到 IP，设备会自己置一个「强制配网」标志并重启，下次开机直接开 `WOL-Setup-XXXX` 热点。UID、主题值、MAC 这些还在 NVS 里，你只需要在页面上重填 WiFi 密码。
>
> 手动进配网也有两条路：上面那两条擦除命令，或者把 `Enable web provisioning` 关掉、改用 menuconfig 写死。

### 5.2 menuconfig（出厂预置）

```bash
idf.py menuconfig
```

进入菜单 **WOL Remote Wake**：

| 配置项                            | 说明                                               |
| ------------------------------ | ------------------------------------------------ |
| `Enable web provisioning`      | 默认开。关掉则只认 menuconfig，配置缺失时直接停机                    |
| `WiFi SSID`                    | **只支持 2.4GHz**。建议给 IoT 设备单独开一个 SSID，避免双频合一连到远端节点 |
| `WiFi password`                | 留空表示开放网络                                         |
| `WiFi max TX power`            | 单位 0.25dBm。默认 56（14dBm），见下方说明                    |
| `WiFi power save mode`         | 默认 `MAX_MODEM`（最省电）；追求响应速度选 `MIN_MODEM`          |
| `WiFi listen interval`         | **省电核心参数**，仅 MAX_MODEM 生效。默认 10（约 1 秒醒一次），详见第 8.1 节 |
| `Bemfa UID`                    | 巴法云控制台的 32 位 UID                                 |
| `Bemfa topic`                  | 巴法云的主题**值**（字母数字串，不是昵称）                        |
| `Target PC MAC`                | 目标机**有线网卡**的 MAC，格式 `AA:BB:CC:DD:EE:FF`          |
| `Magic packet destination`     | 默认 `auto`，按本机 IP+掩码自动推导 `192.168.x.255`          |
| `Enable automatic light sleep` | 默认开                                              |
| `Remote debug awake window`    | `debug` 指令让芯片保持清醒的秒数，默认 600                      |
| `Periodic status report`       | 默认**关**。每次上报都会唤醒 WiFi，明显影响续航                     |

**填了 SSID / UID / 主题值 / MAC 这四项，就等于「出厂预置」**，首次上电不会进配网，直接按这些值跑。

`sdkconfig` 已加入 `.gitignore`，不会被误提交。

> ⚠️ 但**固件里会带上你填的值（明文）**。自己烧自己的板子无所谓，
> 只是别把编译出来的 `.bin` 发给别人——用 `strings` 就能读出 WiFi 密码。

### 关于发射功率（必读）

如果你遇到**反复连不上 WiFi、日志里 reason=2（AUTH_EXPIRE）、但密码确认没写错**：

先别怀疑密码，把 `WiFi max TX power` 调到 56 或更低再试。

这是某些 C3 SuperMini 的硬件问题：射频前端在高于 14dBm 时失真，帧能发出去，但 AP 解调不出来。现象和密码错误一模一样，非常容易误判。本项目默认就把功率压在 14dBm。

## 6. 巴法云与米家接入

整条链路一共穿过三个平台，任何一段没接上，现象都是「点了没反应」：

```
小爱 / 米家 App → 米家云 → 巴法云 → MQTT → ESP32-C3 → UDP 魔术包 → 电脑网卡 → 开机
      ①          ②         ③
```

所以下面按 ① ② ③ 的顺序一段一段验：每段都有「怎么算成功」，对不上就停在那一节排查，别往后猜。

| 段 | 做什么 | 在哪一节 |
|---|---|---|
| ① | 巴法云建一个**开关**主题 | [6.1](#61-第一步巴法云建一个开关主题) |
| ② | 米家里把巴法云账号绑上、同步设备 | [6.2](#62-第二步米家里添加巴法云设备) |
| ③ | 米家里建「手动控制」，把开关装进去，得到一个一键按钮 | [6.3](#63-第三步米家里建一个手动控制一键按钮) |

### 6.1 第一步：巴法云建一个「开关」主题

1. 登录 [cloud.bemfa.com](https://cloud.bemfa.com)（没有账号先注册，免费版够用）
2. 进 **MQTT 设备云** → **添加主题 / 创建设备**
3. **昵称填「电脑」** —— 小爱同学喊的就是这个名字
4. 主题值由平台自动生成，**末尾三位数字是设备类型代号，必须是 `006`**

| 后缀 | 设备类型 | 后缀 | 设备类型 |
|---|---|---|---|
| `001` | 插座 | `005` | 空调 |
| `002` | 灯泡 | **`006`** | **开关 ← 本项目用这个** |
| `003` | 风扇 | `009` | 窗帘 |
| `004` | 传感器 | | |

选错后缀，米家那边会把它识别成插座或灯，语音指令会变成「打开插座」，很别扭。

建好后记下两样东西，后面配网页要填：

- **UID** —— 个人中心里那串 32 位十六进制
- **主题值** —— 形如 `aB3xY9kLm006` 的字母数字串（**不是**昵称，见 [9.9](#99-巴法云的主题值和昵称是两个东西)）

**✅ 怎么算成功**：主题列表里出现这一行，类型显示「开关」，主题值以 `006` 结尾。

> 这一步之后先把固件烧好、配网填完（见 [5.1](#51-配网页推荐)），让巴法云控制台上这个主题的「订阅者」变成在线。**订阅者不在线，后面米家怎么点都没用**，这是最容易冤枉米家的地方。

### 6.2 第二步：米家里添加巴法云设备

1. 米家 App → 右下角 **我的**
2. → **其他平台设备**（有的版本叫「第三方平台设备」）
3. → 右上角 **添加**
4. 搜索 **巴法云**（或「bemfa」）→ 点进去
5. 用巴法云账号登录授权，回到列表点 **同步设备**

**✅ 怎么算成功**：「其他平台设备」列表里出现一个叫 **电脑** 的设备；点进去能看到开 / 关两个按钮，点「开」，巴法云控制台那个主题的状态会跟着变。

> 如果列表里没有，先回巴法云确认主题的「订阅者」是在线状态，再回米家重新点一次「同步设备」，然后下拉刷新。
>
> 如果同步出来的是「插座」而不是「开关」，说明 6.1 里主题后缀选错了，回巴法云重建一个 `006` 结尾的主题。

### 6.3 第三步：米家里建一个「手动控制」（一键按钮）

**为什么要多做这一步**：第三方平台设备不会生成米家首页卡片（原因见 [6.5](#65-为什么米家首页看不到卡片)），更关键的是——**它不能直接当执行动作**。你在「添加执行动作」里翻遍设备列表也找不到「电脑」这个开关。

唯一能走通的通路是：**让小爱音箱替你转述一句指令**，由小爱自己去控制那个开关。这也正是手动控制最常见的用法——把一句语音指令包装成一个按钮。

顺带的好处：把它设成**静默执行**，点按钮时音箱不会出声，半夜点也不会吵到人。

**前置条件**：家里有一台已经绑进米家的小爱音箱（带屏不带屏都行）。

1. 米家 App 底部切到 **智能**
2. 右上角 **+** → 选 **手动控制**（部分版本叫「手动场景」「一键执行」）
3. 先给这个手动控制**起个名字**，比如 **打开电脑**
4. 点 **添加执行动作** → 分类选 **家居设备**
5. 设备选你的 **小爱音箱**
6. 功能选 **执行文本指令**
7. 文本框里填 **打开** + 巴法云里设的那个**开关昵称**，也就是 **打开电脑**
8. 勾上 / 选中 **静默执行**（不选的话音箱会把这句念出来）
9. **完成**

四个地方容易填错，对照一下：

| 位置 | 填什么 | 说明 |
|---|---|---|
| 设备 | **小爱音箱** | 不是「电脑」，第三方设备在这里根本选不到 |
| 功能 | **执行文本指令** | 不是「播放文本」 |
| 文本 | **打开电脑** | 「打开」+ 巴法云昵称，昵称必须一字不差 |
| 结尾 | 选 **静默执行** | 不选就变成语音播报，半夜点会很尴尬 |

**✅ 怎么算成功**：「智能」页出现「打开电脑」这个手动控制。点一下，如果板子还在开机 30 秒调试窗口内，串口会打出：

```
I (16402) main: cmd "on"
I (16412) wol: magic packet sent to 192.168.1.255:9 for aa:bb:cc:dd:ee:ff
```

同时小爱音箱**不会说话**——它只是在后台把这句话执行了。如果音箱开口念了一段，说明第 8 步的「静默执行」没选上，回去补勾。

只想在手机上点、不想动嘴，到这里就完整了。

> **文本里的称呼必须和巴法云昵称一致**：巴法云叫「电脑」，这里就得是「打开电脑」。写成「打开台式机」小爱会回「没有找到设备」，而这一步是静默的，你根本听不到这句报错，只会觉得「按钮点了没反应」。
>
> **点第二次没反应怎么办**：WOL 只负责开机，开关状态会停在「开」，小爱判定无需重复下发。你的米家版本如果能给同一个音箱加两条动作，就先加一条「关闭电脑」、再加「打开电脑」，每次点都必然变化一次；不能加两条的话，用巴法云控制台的在线调试直接发 `on` 应急。
>
> **加到首页（可选）**：部分米家版本支持把手动控制放进首页当快捷卡片——在「智能」页长按或左滑这个手动控制，找「添加到首页 / 添加桌面快捷方式」。没有这个入口也没关系，`智能` 页一点就到。

### 6.4 第四步：小爱语音控制

巴法云设备同步进米家之后，小爱可以直接按**昵称**控制，不用额外配置：

| 说的话 | 效果 |
|---|---|
| 「小爱同学，打开电脑」 | 向设备发 `on` → 发魔术包 |
| 「小爱同学，关闭电脑」 | 向设备发 `off` → 设备回 `wol:off-unsupported`，**电脑不会关机** |

想换成别的说法（「叫醒书房那台机器」之类），在小爱同学 App 里用 **训练计划 / 自定义指令** 把说法映射到「打开电脑」这个开关。

**✅ 怎么算成功**：对小爱说完，巴法云控制台的状态跟着变，串口出现 `cmd "on"`。

> 小爱回「没有找到设备」时，按顺序看两条：① 昵称是不是和米家里已有设备重名（重名会控制错，改巴法云昵称）；② 巴法云里改过昵称之后，米家要重新点一次「同步设备」才会更新。

### 6.5 为什么米家首页看不到卡片

巴法云同步过来的第三方设备不会生成独立的米家卡片，这是平台方的设计，不是配置错了。米家只把「自家生态设备」铺到首页。

三条路，按顺手程度排：

1. **手动控制按钮**（[6.3](#63-第三步米家里建一个手动控制一键按钮)）—— 最接近「首页卡片」的体验
2. **小爱语音**（[6.4](#64-第四步小爱语音控制)）—— 一句话的事
3. **我的 → 其他平台设备** —— 原始入口，四层菜单，应急用

### 6.6 三段排查表

| 现象 | 卡在哪一段 | 先查什么 |
|---|---|---|
| 米家里点了「开」，巴法云状态不变 | ② 米家 ↔ 巴法云 | 重新「同步设备」；确认登录的是同一个巴法云账号 |
| 巴法云状态变了，串口没有 `cmd "on"` | ③ 巴法云 ↔ 设备 | 主题的「订阅者」是否在线；设备订阅的主题值是否和你点的那个一致 |
| 串口有 `cmd "on"`，没有 `magic packet sent` | 设备内部 | 旧固件的 `inet_addr` 缺陷，见 [9.8](#98-inet_addr-会把广播地址判成非法) |
| 魔术包发出去了，电脑不启动 | 电脑侧 | BIOS 的 `ErP` / `ErP Ready` 是否 Disabled，见 [10](#10-常见问题) |
| 手动控制点了没反应，音箱也没出声 | 米家侧 | 文本里的称呼和巴法云昵称不一致；或小爱音箱离线。去小爱的对话记录看有没有「没有找到设备」 |
| 手动控制点下去，音箱把话说出来了 | 米家侧 | 建动作时没选「静默执行」，编辑后补勾 |

## 7. MQTT 命令表

向你的巴法云主题发送以下字符串（米家开关会发 `on` / `off`）：

| 命令       | 行为                                 | 回复                                     |
| -------- | ---------------------------------- | -------------------------------------- |
| `on`     | 发送 WOL 魔术包                         | `wol:sent`                             |
| `off`    | 不支持关机，明确回一条                        | `wol:off-unsupported`                  |
| `debug`  | 持锁保持清醒 `AWAKE_WINDOW_S` 秒，USB 串口恢复 | `debug:awake`                          |
| `sleep`  | 立刻交还锁，回到 light sleep               | `debug:sleeping`                       |
| `status` | 查询当前是否启用 light sleep               | `status:sleep-on` / `status:sleep-off` |

设备还会主动上报两条，不需要发指令：

| 上报                                        | 时机                |
| ----------------------------------------- | ----------------- |
| `ready:v1.0.1,ip=192.168.x.x,ls=1`        | 拿到 IP 并连上 MQTT 后 |
| `boot:sleeping`                           | 启动宽限期结束、即将进入睡眠时   |

> **远程烧录流程**：发 `debug` → 等 2 秒（USB 重新枚举）→ 直接 `idf.py -p COMx flash`。  
> 不需要按任何键，也不需要拆机箱。

## 8. 功耗数据

以下为设计值，**建议自己用万用表实测确认**（不同板子、不同 AP 的设置差异很大）：

| 模式                                        | 平均电流     | 2000mAh 18650 续航 |
| ----------------------------------------- | -------- | ---------------- |
| 常开（不睡）                                    | 80~100mA | 约 1 天            |
| 仅 WiFi modem sleep                        | 约 11mA   | 约 7 天            |
| light sleep + listen interval 3           | 约 0.62mA | 约 37 天           |
| light sleep + listen interval 10          | 约 0.31mA | 约 68 天           |
| light sleep + listen interval 10 + 拆 LED  | 约 0.15mA | 约 110 天          |

### 8.1 省电的核心参数：listen interval（不用改路由器）

WiFi 设备的平均电流几乎完全由**它多久醒一次听 AP 广播**决定。这个频率由两个因素相乘：

```
唤醒周期 = beacon interval（AP 决定，通常 102.4ms） × 醒来间隔（设备决定）
```

「醒来间隔」就是你该调的那个参数，它有两条等价的路子：

| 做法 | 影响范围 | 门槛 |
|---|---|---|
| 改路由器的 **DTIM 周期** | 家里所有 2.4G 设备 | 很多运营商定制固件把这项藏了，改不了 |
| 改固件里的 **listen interval** | **只有这块板子** | 一行配置，完全可控 |

本项目走第二条。`main/Kconfig.projbuild` 里：

```
config APP_WIFI_LISTEN_INTERVAL
    int "WiFi listen interval (beacons)"
    range 1 30
    default 10
    depends on APP_WIFI_PS_MAX_MODEM
```

`idf.py menuconfig` → `WOL Remote Wake` → `WiFi listen interval` 里调，或直接改 `sdkconfig`。

**实测数据**（AP 的 beacon interval = 102.4ms，DTIM = 1 的恶劣情况下）：

| listen interval | 理论唤醒周期 | 实测指令响应延迟 |
|---|---|---|
| 3（ESP-IDF 默认） | 0.31 s | 约 6 s（含云链路抖动） |
| **10（本项目默认）** | **1.02 s** | **1.2 s** |

10 比 3 的唤醒次数降到 1/3.3，而响应仍在 1 秒级——**这才是这个参数最舒服的位置**：省电收益拿到了，语音控制的体感却几乎没变。

调大到 20 以上（约 2 秒醒一次）还能再省一点，但小爱音箱的指令下发会出现明显等待感，不建议。

### 8.2 板载 LED 是隐藏的耗电大户

C3 SuperMini 那颗红色电源灯常亮约 **1.5mA**，是 light sleep 本身（0.3mA）的 5 倍。

**这意味着：不拆 LED 的话，上面所有功耗优化在实测电流上都看不出来。** 想让数字真正降下来，把 LED 旁边的限流电阻拆掉（或直接割断走线）。

## 9. 踩坑记录

这些都是实际踩出来的，按踩坑顺序记录。

### 9.1 light sleep 后串口消失，板子像变砖

C3 的 USB-Serial/JTAG 在 light sleep 时 PHY 时钟被切断，主机端直接认为设备已拔出。更糟的是**醒来时 ESP-IDF 不会自动重新初始化 USB PHY**，需要固件显式重装驱动。

所以「设备睡着了，把它唤醒再连串口」这条路走不通。必须复位重启。

本项目的解法是 `debug` 命令 + `ESP_PM_NO_LIGHT_SLEEP` 锁。

### 9.2 千万不要对睡着的板子做「软件拔插」

用设备管理器或 `Disable-PnpDevice` 禁用再启用那个 USB 设备，会把它从 Windows 设备树里摘掉。芯片在睡眠中无法重新枚举，之后 `GetPortNames()` 直接返回空，`VID_303A` 设备也消失，反复 `pnputil /scan-devices` 都找不回来。

**只能物理复位。** 这是我花了一个上午换来的教训。

三种错误码要分清：

| 报错                            | 含义        | 处理             |
| ----------------------------- | --------- | -------------- |
| `ERROR_GEN_FAILURE`「设备没有发挥作用」 | 设备在、端点不通  | 芯片在 sleep，物理复位 |
| `ERROR_ACCESS_DENIED`「访问被拒绝」  | 端口被别的进程独占 | 关掉占用进程         |
| 端口列表里彻底消失                     | 设备已被摘除    | 物理复位 / 重插      |

### 9.3 事件回调里不能做扫描，栈会溢出

在 `WIFI_EVENT_STA_START` 回调里做阻塞扫描，并且把 `wifi_ap_record_t ap[16]`（约 1.8KB）放在栈上，会直接触发：

```
Guru Meditation Error: Core 0 panic'ed (Stack protection fault).
Detected in task "sys_evt"
Stack bounds: 0x3fca4404 - 0x3fca4f00    <- 只有 2812 字节
```

`sys_evt` 任务栈只有约 2.3KB。正确做法：回调里只置标志/发通知，扫描交给专用任务，AP 数组放静态区。

### 9.4 Arduino 的电源管理是假的

`esp_pm_configure()` 在 Arduino 预编译库里永远返回 `ESP_ERR_NOT_SUPPORTED`，因为 `CONFIG_PM_ENABLE` 根本没开。想省电就必须换 ESP-IDF。

### 9.5 别在睡眠后写日志

USB-Serial/JTAG 在无主机时，写入会**阻塞在驱动里**等一个永远不会来的主机。如果负责「到期归还电源锁」的任务恰好卡在一条日志上，那把锁就永远不会释放，比不睡还费电。

本工程在进入 light sleep 成功后直接 `esp_log_level_set("*", ESP_LOG_NONE)`，整机静音。想看日志请按住 BOOT 上电。

### 9.6 巴法云 MQTT 的鉴权限制

`client_id`、`username`、`password` 三者**都必须是 UID**，换成别的值服务器直接回 `CONNACK rc=5 (not authorised)`。

这也意味着你没法在 PC 上另起一个 MQTT client 旁听同一个主题——会被拒绝。想调试只能看串口或让设备主动 publish。

### 9.7 WiFi 断线重连不能死记 BSSID

早期版本断线后用「记住的 BSSID + 信道」直接重连。AP 一旦切换信道或负载均衡把你踢到另一个节点，就会陷入永久失败。

正确做法：每次重连都重新扫描，挑同 SSID 中信号最强的那个。

### 9.8 `inet_addr()` 会把广播地址判成非法

这条差点让整个项目看起来是坏的：MQTT 收到 `on` 了，日志也打了 `cmd "on"`，但魔术包一个也没发出去，只留下一行 `bad destination: 255.255.255.255`。

原因是 `inet_addr()` 的历史缺陷——它用 `0xFFFFFFFF` 表示「解析失败」，而 `255.255.255.255` 转成二进制恰好也是 `0xFFFFFFFF`。合法的全局广播地址和错误码撞成了同一个值，于是校验永远不通过。

```c
// 错的：255.255.255.255 永远进 if
if (inet_addr(ip) == INADDR_NONE) { /* bad */ }

// 对的：inet_aton 用返回值区分成败
struct in_addr a;
if (inet_aton(ip, &a) == 0) { /* bad */ }
```

顺带把默认目标从写死的 `255.255.255.255` 改成 `auto`：连上 WiFi 后按 `IP & netmask | ~netmask` 推子网定向广播（`192.168.1.43/24` → `192.168.1.255`）。定向广播比全局广播更容易被路由器转发，用户也不用自己算。

启动日志里有一行 `magic dest : 192.168.1.255:9`，排查时先看它。

### 9.9 巴法云的「主题值」和「昵称」是两个东西

巴法云设备列表里每个主题显示两行：一行是主题值（`aB3xY9kLm006` 这种字母数字串），另一行是用户自己起的昵称（比如「客厅电脑」）。

配置页早期把字段写成「主题名」，很自然会填成昵称。后果非常隐蔽：

- 设备连巴法云**成功**，日志 `bemfa: connected` 一切正常
- 但订阅的是一个不存在的主题，米家/小爱发的消息永远到不了
- 控制台一直显示「订阅者：离线」，看起来像设备掉线

抓串口时看到 `bemfa: connected, subscribe "客厅电脑"`——引号里是中文，就是它了。正常情况下引号里必须是一串字母数字。

现在配置页把字段改成「主题值」，加了正误对照示例，并且在提交时检测中文直接拦截。`on_mqtt_cmd()` 里的 `ack:<hex>` 回显也能帮上忙：指令到没到设备，看巴法云调试面板有没有 `ack:6f6e` 就知道。

## 10. 常见问题

**Q：板子连不上 WiFi，一直 AUTH_EXPIRE**  
A：先调低 `WiFi max TX power` 到 56。这是射频失真，不是密码问题。其次确认路由器是 2.4GHz，且没有开启 MAC 白名单。

**Q：米家首页看不到设备**  
A：正常，第三方平台设备不生成独立卡片（见 [6.5](#65-为什么米家首页看不到卡片)）。想要「一个按钮点一下」的体验，在米家里建一个**手动控制**把开关装进去，步骤见 [6.3](#63-第三步米家里建一个手动控制一键按钮)。

**Q：米家里建好手动控制了，点第二次没反应**  
A：WOL 只负责开机，开关状态停在「开」，小爱判定无需重复下发。米家版本支持的话，在手动控制里先加一条「关闭电脑」、再加「打开电脑」两条文本命令；不支持就回巴法云控制台用在线调试直接发 `on`。

**Q：手动控制里选设备，找不到「电脑」**  
A：正常。第三方平台设备不能直接当执行动作，要选**小爱音箱** → **执行文本指令** → 文本填「打开电脑」→ 选**静默执行**，见 [6.3](#63-第三步米家里建一个手动控制一键按钮)。

**Q：发 `on` 后电脑没反应**  
A：按顺序排查，前两条最常见：

1. **BIOS 里的 `ErP` / `ErP Ready` / `EuP` 是否 Disabled** —— 开启时关机后网卡直接断电，魔术包无人接收。这是最容易被忽略的一条。
2. BIOS 里 `Wake on LAN` / `Power On By PCI-E` 是否 Enabled。
3. 目标 MAC 是不是**有线网卡**的（WiFi 网卡关机后完全断电，收不到）。
4. Windows 网卡属性里是否勾选了「允许此设备唤醒计算机」，以及「Wake on Magic Packet」是否为 Enabled。
5. Windows 快速启动是否已关闭（否则「关机」其实是休眠，WOL 无效）。
6. 魔术包目标地址：默认 `auto`，由设备按自己的 IP 和掩码推导子网定向广播。如果启动日志里 `magic dest` 那行显示的不是你网段的 `x.x.x.255`，再手动改 `Magic packet destination`。

**如果串口能看到 `cmd "on"` 但看不到 `magic packet sent`**，那是旧固件的 `inet_addr` 缺陷（见 9.8），升到最新版即可。

验证网卡是否具备唤醒能力的命令：

```powershell
powercfg /devicequery wake_armed
```

**Q：怎么关闭 Windows 快速启动**  
A：管理员 PowerShell 执行 `powercfg /h off`，或控制面板 → 电源选项 → 选择电源按钮的功能 → 取消勾选「启用快速启动」。

**Q：烧录时提示端口被占用 / 找不到端口**  
A：先确认板子没在 light sleep（发 `debug` 或按住 BOOT 上电）。如果端口彻底消失，只能物理重插。

注意两种报错含义完全不同：

| 报错 | 含义 |
|---|---|
| `Could not open COM11 ... FileNotFoundError` | 端口**不存在**，板子没连上（线是充电线 / 接触不良 / 换了 USB 口） |
| `Could not open COM11 ... Access is denied` | 端口存在但**被别的程序占用**（串口助手、上一次的 monitor 没关） |

**Q：烧录报 `This chip is ESP32-C3, not ESP32. Wrong --chip argument?`**  
A：工程的编译目标变成了 `esp32`（原因通常是误点了 `ESP-IDF: Set Espressif Device Target` 后选了 esp32）。检查：

```bash
grep '^CONFIG_IDF_TARGET=' sdkconfig        # 应为 esp32c3
grep 'IDF_TARGET:STRING' build/CMakeCache.txt   # 应为 esp32c3
```

不对就重设（会清掉 build 和 sdkconfig，之后要重新编译）：

```bash
idf.py set-target esp32c3
idf.py build
```

在 VS Code 里等价于执行 `ESP-IDF: Set Espressif Device Target` 并选 `esp32c3`。

> 这个错很隐蔽：`esp32` 目标也能编译成功、生成一个看起来正常的 bin，只是烧不进 C3。判断依据是 `build/flash_args` 里 bootloader 的偏移——C3 是 `0x0`，ESP32 是 `0x1000`。

**Q：能不能远程关机？**  
A：WOL 协议本身不支持。需要在目标机上跑接收端。

## 11. 已知限制

- 只支持 2.4GHz WiFi（C3 硬件限制）
- 魔术包走 UDP 广播，跨网段需要路由器支持定向广播转发
- 不支持远程关机
- 没有 OTA，升级靠 USB
- 巴法云为明文 MQTT（9501 端口），无 TLS
- 配网热点是**开放网络**（无密码），配置期间同一范围内的设备理论上能连上；配置页只在配置不完整时存在，配完立刻关闭
- 配网只在配置不完整时出现，**没有「长按按键重配」或「连不上自动重配」**：换了 WiFi 密码需要 `erase-flash` 后重烧
